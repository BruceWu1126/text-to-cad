# CAM phase 1: core and 2.5D (implementation plan)

Spec: `docs/superpowers/specs/2026-10-13-cam-design.md` (approved 2026-10-13). Branch `amy/cam`, stacked on
`amy/fea-assemblies` (#595). Ends as one draft PR for Jake; nothing merges.

This plan states contracts and tests, not code. A reviewer may flag anything here, and the controller rules on it
rather than deferring to the plan.

## Ground rules for every task

- Read `packages/cadgen/README.md` laws 5, 6, 7, 9, 10, 15 once before the first task.
- Mirror FEA: when unsure how something is done, find the FEA counterpart (`cadgen/fea.py`, `_internal/fea/*`,
  `cli/fea_solve.py`, `results.py` `FeaResult`, `tests/python/support/fea_fixtures.py`) and do the same.
- Import discipline: `cadgen/cam.py`, `_internal/cam/job.py`, `operations/*` and `results.py` are stdlib-only at
  import. OCP, build123d, shapely and numpy are imported inside functions.
- Tests are short, one per contract, build their fixtures in temp dirs (never `models/`), await conditions, no sleeps.
- Units inside the engine: mm, mm/min, rpm, s. Inch exists only in the post.
- Every task ends green on `./.venv/bin/python -m unittest tests/python/packages/cadgen/test_cam*.py` plus the
  tests it names, and is committed on its own with a plain subject (`cadgen: cam ...`).
- No em dashes in prose, findings or docs.

## Tasks

### 1. Skeleton, results, CLI (no behaviour)
- `cadgen/cam.py` with `features` and `plan` (signatures from the spec), docstrings in the `name: text` form the
  generated CLI reads, bodies importing `cadgen._internal.cam.run` lazily.
- `results.py`: `CamFeature`, `CamFeaturesResult`, `CamResult` (frozen, stdlib, `human_lines()`), added to `__all__`.
- `cli/cam_features.py`, `cli/cam_plan.py` (FEA's 28-line stubs); `_COMMANDS` entries; not in `_WARM_COMMANDS`.
- `test_public_surface.py`: `PUBLIC_SURFACE["cadgen.cam"]`, `MIRRORS` rows.
- Test: `cadgen cam plan --help` lists `--job`, `--post`, `--occurrence`, `--out`, `--json`; importing `cadgen.cam`
  pulls in none of OCP, numpy, shapely (subprocess check, like FEA's `heavy_at_import`).

### 2. Job parsing (stdlib)
- `_internal/cam/job.py`: `parse_job(job) -> Job` from a path, inline JSON or dict. Dataclasses for machine,
  material, stock, setups, tools, operations, view. Closed vocabularies for every enum in the spec.
- Operation keys are validated by the operation registry (task 3): `job.py` checks the common keys
  (`op`, `setup`, `tool`, `features`, `region`, `all`, feeds overrides, `stock_to_leave_mm`) and hands the rest
  to the operation's `parse`.
- Cross-references: an operation's `setup` and `tool` must exist; a tool's type must suit the operation
  (a tap cannot pocket). Errors name the field path.
- `machine.post` is required; its absence is an error that says why ("a wrong post can crash a machine").
- Test `test_cam_job.py`: one valid job round-trips; a table of bad jobs, each with the exact message fragment
  (unknown key, wrong enum, missing post, dangling tool, tool type mismatch, negative depth).

### 3. Operation registry and protocol (stdlib)
- `_internal/cam/operations/__init__.py`: `REGISTRY` of `Entry(name, phase, module, cls, word)` for all 55 names
  in spec order; `get_operation(name)` raises a sentence for unknown names and for unbuilt ones ("`adaptive_3d` is
  phase 2, not built yet").
- `operations/base.py`: the protocol: `keys`, `parse(raw, ctx) -> params`, `plan(params, ctx) -> list[Move]`,
  `checks(params, ctx, moves) -> findings`, `human_lines(stats)`, `tool_types` accepted.
- Test `test_cam_protocol.py`: registry order and count, every built module stdlib-only at import, unbuilt refusal
  text, unknown name text.

### 4. Geometry access and `cam features`
- `_internal/cam/part.py`: open a STEP and pick the occurrence exactly as `_internal/fea/run.py` does (`_open`,
  leaves, `--occurrence`); share by importing FEA's helper only if it is stdlib-light at import, else factor the
  helper into `_internal/step_open.py` used by both (a pure move, FEA tests stay green).
- `_internal/cam/features.py`: from the B-rep, per setup direction (default: the six axes):
  planar faces facing the tool (`face`), cylindrical holes (diameter, depth, through or blind, axis, `hole`),
  pockets (closed wall loops over a planar floor, depth, smallest inside corner radius, `pocket`), open slots
  (`slot`), outer profile at each Z (`profile`). Each with selector(s), size and `reach` (directions that see it).
- Test `test_cam_features.py`: a fixture plate (100x60x10 with a 40x20x5 pocket, R3 corners, two 6 mm through
  holes and one 5 mm blind hole) lists exactly those features with the right sizes and `+Z` reach.

### 5. Stock, setups, WCS
- `_internal/cam/stock.py`: box (part bbox plus margins), cylinder, from STEP; `setups.py`: frame per setup
  (direction, origin keyword or point), transforms part and stock into setup frame.
- Reachability: a feature listed in an operation must be reachable from that setup's direction, else an
  `unreachable` finding.
- Test: origin keywords put the WCS where stated (stock top centre is z=0 at the stock top); a `-Z` setup flips.

### 6. Tools and feeds
- `_internal/cam/tools.py`: profiles for phase-1 types (flat, ball, bull, chamfer, V-bit, drill, spot drill, tap,
  reamer, boring bar, thread mill, back-bore). Each gives radius-at-height (for checks) and a mesh (for the GLB).
- `_internal/cam/feeds.py` with a material table (aluminium 6061 and 7075, mild steel, stainless 304, brass,
  acetal, HDPE, MDF, plywood, hardwood): SFM and chip load by tool diameter band, carbide and HSS factors,
  radial chip thinning for adaptive, plunge at a fraction of feed, tap feed = rpm x pitch. Clamp to machine
  max rpm and feed; each clamp becomes a finding.
- Test `test_cam_feeds.py`: textbook numbers for 6 mm 3-flute carbide in 6061 within 10%, chip thinning formula,
  clamp produces `rpm_clamped`, tap feed exact.

### 7. Toolpath format and arc fitting
- `_internal/cam/toolpath.py`: `Move` (kind, xyz, feed, op, t, plus arc centre / cycle params), time integration
  (feed moves at feed, rapids at machine rapid rate), lengths, bounds; `fit_arcs(points, tol)` that turns
  polylines into G2/G3 where within tolerance; linking (retract to clearance, rapid, plunge or ramp) shared by all
  operations.
- Test: a polygonal circle fits back to one arc; time and length of a known path; linking never rapids below
  clearance.

### 8. Posts (5)
- `_internal/cam/posts/`: base class with capabilities, and `grbl`, `linuxcnc`, `fanuc`, `haas`, `mach3`.
  Header comment block per spec (with the prove-out line), units, WCS (G54), tool change (with `M6` where
  supported; grbl writes a pause and comment), spindle, coolant, linear, arc (I/J), canned cycles G81/G82/G83/G73/
  G84/G85/G86/G76/G87 or expanded when unsupported, footer. Line numbers where the dialect wants them. Number
  formatting deterministic.
- `--post` overrides `machine.post`.
- Test `test_cam_posts.py`: golden snippets per post (header, tool change, arc, a peck cycle); same input twice is
  byte-identical; a G-code back-plot reader in `support/cam_fixtures.py` reads every post's output into moves.

### 9. Operations: facing, contour_2d, pocket_2d, slot, circular, bore, trace
- Built on shapely offsets of the feature's section at each depth step. Contour: side, tabs, lead-in/out arcs,
  finishing passes. Pocket: offset (default) or zigzag. Bore: helical. Circular: round pocket or boss.
- Test per op (one file `test_cam_milling_2d.py`): the back-plotted G-code equals the planned moves; the swept
  tool never enters the part beyond tolerance (distance check against the B-rep); the floor/walls are reached
  within stock-to-leave.

### 10. Operations: adaptive_2d, chamfer_2d, engrave, thread_mill
- Adaptive: constant-engagement offset approach (clean room): engagement capped at a stated percentage, trochoidal
  in narrow passages, stays down between passes where safe.
- Test: max engagement along the path stays under the cap (computed against a simple area-swept model); others as
  task 9.

### 11. Drilling: drill, spot_drill, peck, chip_break, tap, rigid_tap, ream, boring_cycle, counterbore, back_bore
- Holes from `features`, ordered by a nearest-neighbour tour per tool; depth from the hole (through adds the
  drill point length plus breakthrough).
- Test `test_cam_drilling.py`: each cycle posts as the right G-code where supported and expands correctly where not;
  hole order is a tour, not file order; a blind hole never exceeds its depth.

### 12. Checks
- `_internal/cam/checks.py`: phase-1 findings from the spec: `gouge` (distance from tool envelope to part along
  feed moves), `holder_collision` and `fixture_collision` (holder/shank and fixture boxes against stock and part),
  `unreachable`, `too_deep`, `over_travel`, `no_post_support`, `empty_operation`, `corner_left` (from feature
  corner radius vs tool), `rpm_clamped`, `feed_clamped`, `full_slot`, `long_stickout`, `uncut_feature`.
- Wording reviewed with an engineer's lens. Errors first. `ok=False` when any error.
- Test `test_cam_checks.py`: each finding fires on a fixture built to trigger it and stays quiet on the clean plate.

### 13. Outputs and `cam plan` end to end
- `_internal/cam/outputs.py`: a small byte-deterministic glTF writer (triangle meshes and `LINES`), metres and glTF
  axes as FEA's `_gltf_space`. Part mesh first with the extras; stock, fixture, tool meshes; one `LINES` primitive per
  operation with `_T`, `_KIND`, `_OP`.
- Sidecar and `.nc` writing per spec, file naming rules, `files{}`.
- `_internal/cam/run.py`: parse job, open part, build setups, plan each operation, checks, post, write, return
  `CamResult`; `CliLogger("cam")` progress.
- Test `test_cam_plan.py`: the fixture plate with a 4-operation job writes three files; GLB extras carry the marker
  on mesh 0; lines carry the three attributes; sidecar matches `CamResult`; a bad job exits 1 with findings and
  writes no `.nc`.

### 14. Viewer
- `packages/ui/src/renderers/glb/`: `carriesCamResult`, `loadCamView` and `useCamView` beside FEA's in
  `GlbRenderer.jsx`; `camView.jsx` barrel; `camResult.js` (pure readers of extras and line attributes);
  `camPaths.js` (hide glTF lines, fat lines from `createScreenSpaceLineSegments`, colour by kind from theme tokens,
  clip by time); `CamJobPanel.jsx` (setups, tools, operations with time and visibility, summary, the shared findings
  card); one own playbar clip moving the tool mesh; Time row and per-operation Presets through FEA's motion contract;
  Display gates (Rapids, Stock, Fixtures, Tool); readout overlay that steps above the playbar.
- `packages/ui/docs/settings-ui.md`: CAM section and tools-table row.
- Tests: `camResult.test.ts`, `GlbRenderer.cam.test.tsx`, new rows in `GlbRenderer.lazy.test.tsx` (plain 0, FEA
  loads only FEA, CAM loads only CAM). Fixture builder `glb/__tests__/camFile.ts`.
- Look at it on screen (snapshot or the dev viewer) before calling it done: paths, tool at a mid time, Job panel at
  164 px, a phone width.

### 15. Skill and registries
- `skills/cam/`: SKILL.md, `agents/openai.yaml`, references per spec (phase-1 pages full; later phases' pages say
  "not built yet" and are listed in `planned-next.md`).
- `gcode` skill description: one line pointing subtractive work to `$cam`.
- `skills.sh.json`, root `README.md` skill table, `apps/docs/src/lib/content.ts`, `packages/cadgen/README.md`
  (shape tree, Verbs by format), `select_checks.py` rules (and `test_ci_workspace_selection.py` expectations).
- Test: `SkillDocs` in `test_cam_protocol.py` (every built operation has a "Runs today" row), the existing skill
  description length and pin tests pass.
